# Lesson 10.12: You Are PID 1

**Time:** 2–3 sessions of 45 min · **You need:** a terminal; the Arch
ISO from Lesson 10.11 (in `~/lab/os/arch`); `hello` (Lesson 10.2) and
`shelly` (Lesson 10.10) in `~/lab/os`; QEMU · **New words:** boot,
firmware, bootloader, initramfs, init, static linking, kernel panic

## Goal *(read this to the learner)*

> When a Linux computer starts, the kernel wakes up, and then runs
> exactly one program: PID 1. Everything else comes from that one. Today
> you'll boot a real Linux kernel in QEMU, and the only program it has
> will be *yours*: first a tiny greeting, then Shelly. You'll find out
> what happens if PID 1 ever stops.

## Warm-up (5 min)

"When the Arch VM started, what did you see, in order?" *(A menu (GRUB),
then lots of kernel messages, then `[ OK ]` lines, then a login.)* "In
`pstree`, what was at the top?" *(`systemd`, PID 1.)*

## Activity

### Session 1: how a computer boots

1. **The boot relay.** **Say:** "Starting a computer is a relay race.
   Each runner does a little, then hands over to a bigger one." Draw five
   runners in a row, and label them as you go:
   - **Firmware** (BIOS or UEFI): a program in a chip on the main board.
     It checks the hardware and finds a disk to start from.
   - **Bootloader** (GRUB on Arch, systemd-boot on Pop!_OS): loads the
     kernel from the disk into memory.
   - **The kernel**: sets up the CPU, memory and devices. You saw its
     messages scroll past.
   - **The initramfs** (initial RAM file system): a tiny file system,
     loaded into memory with the kernel, holding the first programs.
   - **PID 1** (`init`): the first program. On Pop!_OS and Arch it's
     `systemd`, which starts everything else: the login screen, the
     network, and so on.

2. **Look at it on this computer.**
   ```
   systemd-analyze
   cat /proc/cmdline
   ls /boot
   ```
   **They should see:** a line like `Startup finished in 8.105s
   (firmware) + 3.012s (loader) + 1.893s (kernel) + 5.317s (userspace) =
   18.328s`, the times for each runner; then the **kernel command line**,
   the settings the bootloader gave the kernel; and in `/boot`, files
   starting `vmlinuz` (the kernel) and `initrd` (the initramfs). **Ask:**
   "Which runner is slowest?" *(Usually the firmware or userspace.)*

### Session 2: your program as PID 1

3. **Get a kernel.** The Arch ISO has a kernel inside it. Take it out:
   ```
   mkdir -p ~/lab/os/pid1
   cd ~/lab/os/pid1
   bsdtar -xf ../arch/archlinux-*.iso arch/boot/x86_64/vmlinuz-linux
   mv arch/boot/x86_64/vmlinuz-linux .
   rm -r arch
   ls -l
   ```
   **They should see:** `vmlinuz-linux`, about 17 MB. **Say:** "That's a
   whole Linux kernel, the same one the Arch VM runs. `bsdtar` can read
   inside an ISO like a zip file."

4. **The greeting.** A new project:
   ```
   cd ~/lab/os
   cargo new hello-init
   cd hello-init
   ```
   ```rust
   use std::fs;
   use std::io;

   fn main() {
       println!();
       println!("Hello from PID {}!", std::process::id());
       println!("Here is everything in /:");
       for entry in fs::read_dir("/").unwrap() {
           println!("  {}", entry.unwrap().file_name().display());
       }
       println!("Press Enter to stop me.");
       let mut line = String::new();
       io::stdin().read_line(&mut line).unwrap();
       println!("Goodbye!");
   }
   ```

5. **A program that needs nothing.** **Say:** "Our tiny Linux will have
   *no* other files: no libraries at all. Look at what `hello` needs:"
   ```
   cd ~/lab/os/hello
   ldd target/debug/hello
   ```
   **They should see** a list including `libc.so.6` and
   `/lib64/ld-linux-x86-64.so.2`. **Say:** "Those are **shared
   libraries**: code that lives in other files, loaded when the program
   starts. Our tiny Linux won't have them. So we build with **musl**, a
   small C library that can be built *into* the program: **static
   linking**."
   ```
   cargo build --release --target x86_64-unknown-linux-musl
   ldd target/x86_64-unknown-linux-musl/release/hello
   ```
   **They should see:** `statically linked`. Now the same for
   `hello-init`:
   ```
   cd ~/lab/os/hello-init
   cargo build --release --target x86_64-unknown-linux-musl
   ```

6. **Pack the initramfs.**
   ```
   cd ~/lab/os/pid1
   mkdir -p hello-root
   cp ../hello-init/target/x86_64-unknown-linux-musl/release/hello-init hello-root/init
   cd hello-root
   find . | cpio -o -H newc > ../hello.cpio
   cd ..
   ```
   **They should see:** a number of `blocks`. **Say:** "The kernel looks
   for a program called `/init` in the initramfs, and runs it as PID 1.
   `cpio` is an old way of packing files into one, which the kernel
   understands."

7. **Boot it!**
   ```
   qemu-system-x86_64 -enable-kvm -m 512 -kernel vmlinuz-linux -initrd hello.cpio -append "console=ttyS0 quiet" -nographic
   ```
   **Say:** "`-kernel` and `-initrd` hand QEMU the kernel and initramfs
   directly, so there's no bootloader. `-append` is the kernel command
   line: `console=ttyS0` sends its text to this terminal, and `quiet`
   hides most of its messages. `-nographic` means no window." **They
   should see**, after a few lines about `SeaBIOS` and `Booting from
   ROM...`:
   ```
   Hello from PID 1!
   Here is everything in /:
     init
     root
     dev
   Press Enter to stop me.
   ```
   **Say:** "Your program is PID 1! The whole world is three things: your
   program, and two folders the kernel made."

8. **What if PID 1 stops?** **Ask:** "What will happen when you press
   Enter?" Let them guess, then press it. **They should see:**
   ```
   Goodbye!
   [    4.109389] Kernel panic - not syncing: Attempted to kill init! exitcode=0x00000000
   ```
   followed by many lines of numbers, ending with `---[ end Kernel panic
   - not syncing: Attempted to kill init! exitcode=0x00000000 ]---`.
   **Say:** "A **kernel panic**: the kernel has stopped, because it can't
   go on without PID 1. That's why `systemd` never finishes." To leave
   QEMU, press **Ctrl+A**, let go, then press **X**. **They should see:**
   `QEMU: Terminated`.

### Session 3: Shelly as PID 1

9. **The smallest Linux with a shell.** Build Shelly and `hello`
   statically (you built `hello` in step 5):
   ```
   cd ~/lab/os/shelly
   cargo build --release --target x86_64-unknown-linux-musl
   cd ~/lab/os/pid1
   mkdir -p shelly-root/bin
   cp ../shelly/target/x86_64-unknown-linux-musl/release/shelly shelly-root/init
   cp ../hello/target/x86_64-unknown-linux-musl/release/hello shelly-root/bin/
   cd shelly-root
   find . | cpio -o -H newc > ../shelly.cpio
   cd ..
   qemu-system-x86_64 -enable-kvm -m 512 -kernel vmlinuz-linux -initrd shelly.cpio -append "console=ttyS0 quiet" -nographic
   ```
   **They should see:** `shelly:/> `. Try `ls`, `pwd`, `hello`, `cd
   /bin`, `cd`, `cd /dev` and `echo hi`. **They should see:**
   ```
   shelly:/> ls
   shelly: ls: command not found
   shelly:/> pwd
   shelly: pwd: command not found
   shelly:/> hello
   Hello, world!
   shelly:/> cd /bin
   shelly:/bin> cd
   shelly:/> cd /dev
   shelly:/dev> echo hi
   shelly: echo: command not found
   ```
   **Ask:** "Why doesn't `ls` work?" *(There's no `ls` program in this
   world! Only Shelly and `hello`.)* "Why do `cd` and `hello` work?"
   *(`cd` is built into Shelly; `hello` is a program in `/bin`.)* **Say:**
   "Every command you've ever typed is a program in a folder. A Linux
   system is a kernel, plus a lot of programs like these."

   Type `exit`. **They should see** the kernel panic again: Shelly was
   PID 1. Ctrl+A, then X. Commit `hello-init` (not the `.cpio` files or
   the kernel).

## If something goes wrong

| What you see | What it means | What to do |
|---|---|---|
| `bsdtar: command not found` | It isn't installed | See "Before the lesson". |
| `bsdtar: Error opening archive: Failed to open '../arch/archlinux-*.iso'` | The ISO isn't there | Check `ls ~/lab/os/arch`; Lesson 10.11 downloads it. |
| ``error[E0463]: can't find crate for `std` ``, with a note that ``the `x86_64-unknown-linux-musl` target may not be installed`` | The musl target isn't installed | Run `setup-os.sh` (the Stage 10 README). |
| `Could not access KVM kernel module` | KVM isn't available to this account | Leave out `-enable-kvm` (slower, but it works), and see Lesson 10.11's error table. |
| `Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(0,0)` | There's no `/init` in the initramfs, so the kernel looked for a real disk instead, and there isn't one | Check the `cp ... hello-root/init` line, then make the `.cpio` again. |
| `Kernel panic - not syncing: No working init found.` | `/init` is there, but can't run: usually it isn't static, so the libraries it needs are missing | Build with `--target x86_64-unknown-linux-musl`, and copy *that* file (from `target/x86_64-unknown-linux-musl/release/`). |
| Nothing appears, and QEMU seems stuck | `console=ttyS0` is missing, so the text went to a screen that isn't there | Ctrl+A, X, and check the `-append` part. |
| The terminal acts strangely after QEMU | QEMU left it in a funny mode | Type `reset` and Enter. |

## Guide's background *(optional reading)*

Real initramfs images (like Pop!_OS's `/boot/initrd.img`) contain a
small init that loads the drivers needed to find the real root disk,
mounts it, and then hands over to the real PID 1, `systemd`, with a
system call named `switch_root`. Ours skips all that: the initramfs *is*
the whole system.

The kernel always unpacks a tiny built-in initramfs first, holding
`/dev`, `/dev/console` and `/root`, and then ours on top. That's why
`/dev` and `/root` appear, and why the program's output reaches the
terminal: `/dev/console` is connected to `ttyS0`, QEMU's serial port,
which `-nographic` joins to the terminal. Nothing mounts `/proc` or
`/sys`, so programs that read them fail. Mounting needs the `mount`
system call, which Rust's standard library doesn't wrap.

Static linking with musl makes `hello` about half a megabyte, against
4.5 MB for the debug build with glibc (most of that is debugging
information). The exit code in "Attempted to kill init! exitcode=0x00000000"
is the program's exit status: 0 means it finished normally, and
`0x00000100` is exit status 1.
